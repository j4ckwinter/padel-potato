# Roadmap: Padel Potato

## Overview

This milestone establishes Padel Potato's native-first React Native design system as a dependable future screen-building kit. Work first proves the Expo and Storybook validation routes, then captures Penpot authority in tokens and assets, establishes shared interaction contracts, delivers each reusable component family as a vertically verified batch, and closes with a catalogue-wide coverage and evidence audit. Product screens and game flows remain deferred.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 1: Native Workbench and Validation Seams** - Prove the version-locked Expo/Storybook catalogue and its native and browser review paths.
- [ ] **Phase 2: Penpot Provenance, Foundations, and Assets** - Turn authoritative Penpot foundations into traceable tokens, assets, primitives, and stories.
- [ ] **Phase 3: Interaction and Accessibility Contracts** - Establish the typed, accessible behavior and test conventions every component family will share.
- [ ] **Phase 4: Verified Component Families** - Deliver all Penpot reusable component families in dependency-ordered, native-verified vertical batches.
- [ ] **Phase 5: Catalogue Coverage and Evidence Audit** - Prove complete, reviewable catalogue coverage and retain final cross-platform evidence.

## Phase Details

### Phase 1: Native Workbench and Validation Seams
**Goal**: Developers can reliably review the shared component catalogue on its authoritative native platforms and use a secondary local browser lane.
**Depends on**: Nothing (first phase)
**Requirements**: WORK-01, WORK-02, WORK-03, WORK-04, WORK-05, WORK-06
**Success Criteria** (what must be TRUE):
  1. A developer can install the locked Expo/React Native TypeScript project and pass its automated Expo dependency-health check.
  2. A developer can launch the same sample Storybook catalogue on iOS and Android through the documented native workbench route.
  3. A developer can browse representative shared stories locally through Expo web, with its secondary-review role documented.
  4. A production-mode app launch excludes Storybook code while the Storybook-enabled route remains available for review.

### Phase 2: Penpot Provenance, Foundations, and Assets
**Goal**: Developers can build from an authoritative, token-backed Penpot foundation layer instead of rediscovering design values per component.
**Depends on**: Phase 1
**Requirements**: PNPT-01, PNPT-02, PNPT-03, PNPT-04, FNDT-01, FNDT-02, FNDT-03, FNDT-04, FNDT-05, FNDT-06, PRIM-01, PRIM-03, PRIM-04
**Success Criteria** (what must be TRUE):
  1. Developers can inspect a versioned Penpot manifest and reference-render set covering foundations, component sources, variant axes, and designed states.
  2. Developers can use named colour, typography, spacing, radius, dimension, border-width, and opacity tokens, with semantic aliases rather than unexplained component-local literals.
  3. iOS and Android foundation stories render the intended fonts, typography metrics, and complete token gallery.
  4. Developers can compose token-backed text, layout, surface, icon, and brand-lockup primitives from the complete approved Penpot asset set.
  5. Each implemented token or primitive can be traced to its Penpot source, and every intentional difference is retained in a source-linked deviation record.

### Phase 3: Interaction and Accessibility Contracts
**Goal**: Every subsequent component family can expose a bounded, accessible, and testable native interaction contract.
**Depends on**: Phase 2
**Requirements**: PRIM-02, QUAL-01, QUAL-02, QUAL-03, QUAL-04, QUAL-05, QUAL-06, QUAL-07
**Success Criteria** (what must be TRUE):
  1. Developers can use shared interactive primitives with consistent press, disabled, loading, focus, touch-target, and accessibility behavior.
  2. A component's public props can express only its supported Penpot variants and states, rather than arbitrary combinations.
  3. Component stories follow one navigable taxonomy and can present canonical, variant, state, content-boundary, and useful interactive-control examples.
  4. The shared test harness can verify semantic roles, labels, values, states, and interaction behavior for interactive components.
  5. The component contract includes usable native targets plus large-text and assistive-technology checks for representative components.

### Phase 4: Verified Component Families
**Goal**: Developers can select every designed reusable Penpot component and supported state from a coherent, native-ready library.
**Depends on**: Phase 3
**Requirements**: ACTN-01, ACTN-02, ACTN-03, FORM-01, FORM-02, FORM-03, FORM-04, AUTH-01, AUTH-02, NAVG-01, NAVG-02, NAVG-03, NAVG-04, IDEN-01, IDEN-02, IDEN-03, STAT-01, PROG-01, CONT-01, CONT-02, CONT-03, CONT-04, CONT-05, CONT-06, CONT-07, FDBK-01, FDBK-02, CARD-01
**Success Criteria** (what must be TRUE):
  1. Developers can use the complete actions and forms family - Button, Icon Button, Favourite, Field, Choice Chip, Checkbox, Day Time Selector, Social Sign-In Button, and Auth Divider - in every designed variant and state.
  2. Developers can use navigation, identity, status, and progress components in their designed configurations, selected states, sizes, and content combinations.
  3. Developers can use all designed content, feedback, and illustrated-card components with their supported types, result/read/content states, and icon options.
  4. Each dependency-ordered component-family batch ships with its bounded typed API, navigable stories, semantic and interaction tests, and iOS/Android reference comparison evidence.
  5. A reviewer can find each public component in Storybook without needing product screens, navigation, live data, or invented prop combinations.
**Plans**: TBD
**UI hint**: yes

### Phase 5: Catalogue Coverage and Evidence Audit
**Goal**: Reviewers can confidently establish that the native component catalogue is complete, comparable to Penpot, and ready for future product screens.
**Depends on**: Phase 4
**Requirements**: VRFY-01, VRFY-02, VRFY-03, VRFY-04, VRFY-05
**Success Criteria** (what must be TRUE):
  1. Every component family has an iOS and Android comparison against its Penpot references, with corrections or approved deviations recorded.
  2. A coverage audit accounts for every Penpot foundation, component, variant, and designed state as implemented or explicitly dispositioned.
  3. Shared stories pass the local Expo-web discovery and render smoke review, with web-specific deviations documented rather than treated as native acceptance.
  4. The final evidence pack identifies platforms, devices, capture conditions, comparison results, and approved deviations for catalogue review.
